# eveneffort — Design System

A unified, disciplined visual language for the app. Red, white, black — plus one
six-stop ramp, on one pill, argued for at the bottom of this file. Nothing else.

## Principles

1. **Surface-dominant.** The page is white. The surface dominates and whitespace is the primary tool. Color is rare and meaningful. The page is white by default. A dark theme exists, but only for a reader who presses the nav toggle; see "Theme".
2. **Red is reserved.** Red appears only on interactive primary actions (Calculate button, active toggle), and as a meaningful data signal (uphill elevation deltas, the two hilliest course profiles). It should not be used for decoration. The course-profile pill is the one place the palette runs a multi-hue scale, and it is a closed set — see "What NOT to do".
3. **Type carries the brand.** Montserrat carries the whole site — headings and body. The original Fraunces serif is kept only for the "eveneffort" wordmark. Tabular numerals everywhere numeric data appears.
4. **Borders over shadows.** Hierarchy is built with 1px borders and generous radius, not drop shadows.
5. **One source of truth.** All colors, fonts, and radii live in `src/app/globals.css` as design tokens. No hardcoded values in components.

## Theme

**Two themes, light by default, dark by choice.** This reverses a position that stood until 2026-09-21 ("light mode only, no toggle"), so the old argument and what replaced it are both written down here.

- **The old rule, and why it held.** The product's argument is that the page is white and colour is rare. A theme that follows the operating system would change the site for every visitor who never asked, and per-component `dark:` branching would put a second source of truth beside the tokens.
- **What changed:** readers asked for it, and it can be built without either cost. The choice is **opt-in** (the site is white until someone presses the toggle) and it lives **entirely at the token layer** (a second value for every token, never a branch in a component).
- **Two-state, manual, default light.** `prefers-color-scheme` is not read anywhere, not even as the initial value. Absent a stored choice the page is light. `src/app/globals.tokens.test.ts` and `src/theme.guard.test.ts` fail if a `prefers-color-scheme` or a `dark:` utility appears.
- **Mechanism.** `data-theme="dark"` on `<html>`. The DOM attribute is the source of truth (`src/lib/theme.ts`); `localStorage` (`prefs.theme`, via `stateKeys.ts`) is only how it survives a reload. A blocking inline script in `layout.tsx`, built from the same key, sets the attribute before first paint, because the home page is prerendered and the server cannot know the choice. `color-scheme` follows the theme so native controls, date and time inputs and scrollbars come with it.
- **Every token is redeclared in the dark block**, including those that keep their light value. A token added to `@theme` and forgotten there does not error, it leaves a patch of white chrome on a black page, so the parity test fails on it.
- **Dark palette: a surface ladder, not one black.** This is the part a dark theme gets wrong by default, and the first pass here did. Page `#121212`, card/input/nav/modal `#1C1C1C`, elevated (table heads, hover, chips) `#242424`, each step genuinely lighter than the last. Dark cannot lean on shadows the way light does, because a shadow on near-black is invisible, so depth comes from lightness. Light needs no ladder (page and card are both `#FFFFFF`, elevated a hair off) because white is already the top of its scale and a border does the work. Text is `#E6E6E6` / `#ADADAD` / `#919191` on a `#333333` border. The values follow the standard guidance rather than being invented: a soft near-black around `#121212` instead of `#000` (pure black leaves nowhere to go for elevation, and near-white on it measures ~19:1, the glare people mean when they call a dark theme harsh), off-white rather than near-white body text, and desaturated accents.
- **Red has two roles, so it has two tokens.** As text or a data mark (`--color-red-primary`: uphill delta, the Hilly pill, chart bars, map pins) it lightens and desaturates to `#E08571` in dark, because `#B91C1C` on a dark page is unreadable. As a fill under white type (`--color-red-fill`, `--color-red-fill-hover`) it must stay dark, because a red light enough to read as text cannot also carry white type at AA. No single red can do both, so those two tokens are identical in both themes and only a control paired with `text-white` uses them.
- **The footer inverts.** In light it is the single darkest element, anchoring the foot of a white page, and it keeps its own `*-on-dark` / `*-footer*` tokens scoped to `SiteFooter`. In dark it is therefore the single LIGHTEST element, above even the elevated surface: `--color-bg-footer` `#383838`, `--color-bg-footer-deep` `#2E2E2E`, with `--color-border-on-dark` lifted to `#555555` so its column rules survive the lighter fill. It has to clear **two** neighbours, which is the trap: on most pages it meets the page, but on the home page it meets the closing CTA, which is already an elevated band. A first pass at `#1F1F1F` was 1.06:1 against that and merged into it. These values maximise the worse of the two separations, and the test asserts both.
- **The map.** `BASEMAP_STYLES` in `CourseMap.tsx` pairs OpenFreeMap `positron` (light) with `dark` (its near-black sibling; the CARTO name `dark-matter` is a 404 there). A theme change calls `setStyle` and re-adds the source and layers on `style.load`, re-reading the pin tokens, so pan, zoom and any open popup survive.
- **Print is always light.** The dark block is wrapped in `@media not print`, so paper never sees it and a dark-mode order does not come off the printer as a black rectangle. Nothing is restated for paper.
- **The paceband preview stays white paper.** `PaceBandPreview` stands for a printed sheet, so `.paceband-preview` restates the light values of the five tokens the strip reads. The parity test fails if one drifts from `@theme`.
- **`--color-scrim` exists because `text-primary` at 40% is black in light and white in dark**, and a white veil over a dark page is a flashbang.
- **The OG image** (`opengraph-image.tsx`) is static and stays light.
- **The toggle** (`ThemeToggle`) is a 32px icon button in the nav at every width (the menu button's box, so the bar's height arithmetic is untouched). It is a pressed-state button under the fixed label "Dark mode", not a label that flips. Both glyphs are in the markup and CSS picks one off `data-theme`, so there is no wrong-icon flash.
- **Nav breakpoint moved from `lg` to `xl`.** Measured: with six links the desktop row already wrapped at 1024-1050px, and the toggle stretched that to ~1100px. Below 1280px the links live behind the menu button.

Rule for new components: never hardcode a surface (`bg-white`) or text color, and never branch on the theme. Go through a token, so the single source of truth in `globals.css` stays authoritative.

## Typography

Montserrat drives the entire site — body and headings — via
`--font-sans` and `--font-display`. The original Fraunces serif is
retained **only** for the "eveneffort" wordmark, exposed as
`--font-wordmark`. Do **not** introduce sizes outside this scale.

| Role | Tailwind | Family |
|---|---|---|
| Wordmark (eveneffort logo) | `font-wordmark text-[2rem] tracking-tight` | Fraunces 500 |
| Display heading | `text-2xl/3xl font-display tracking-tight` | Montserrat 600 |
| Section heading | `text-lg font-semibold` | Montserrat 600 |
| Pace / split values | `text-base font-tabular font-medium` | Montserrat 500, tabular |
| Body | `text-base` | Montserrat 400 |
| Helper / label | `text-sm text-[var(--color-text-secondary)]` | Montserrat 400 |
| Column header / eyebrow | `text-xs uppercase tracking-wider text-[var(--color-text-tertiary)] font-medium` | Montserrat 500 |

`.font-tabular`, `.font-display`, and `.font-wordmark` are utility
classes defined in `globals.css`.

## Spacing & radius

- Card radius: `rounded-2xl` (16px)
- Control radius: `rounded-lg` (8px) — buttons, inputs, toggles
- Card padding: `p-8` desktop, `p-6` mobile
- Section spacing: `space-y-10` between major sections in a page

## Component patterns

- **Card:** `rounded-2xl border border-[var(--color-border)] bg-white p-8 space-y-8`. No shadow.
- **Primary button:** `w-full rounded-lg bg-[var(--color-red-primary)] hover:bg-[var(--color-red-deep)] disabled:bg-[var(--color-border)] disabled:text-[var(--color-text-tertiary)] text-white py-4 text-base font-semibold transition-colors`.
- **Secondary toggle (pill group):** container `inline-flex rounded-lg border border-[var(--color-border)] overflow-hidden`; active button `bg-[var(--color-red-primary)] text-white`, inactive `bg-white text-[var(--color-text-secondary)] hover:bg-[var(--color-bg-elevated)]`; each `px-6 py-2.5 text-sm font-medium transition-colors`. Reserved for consequential switches — currently only the weather On/Off.
- **Micro unit toggle (`UnitToggle`):** for picking a field's display unit inline beside its label. Container `inline-flex rounded-md border border-[var(--color-border)] overflow-hidden`; buttons `px-2 py-0.5 text-xs font-medium`; active `bg-[var(--color-bg-elevated)] text-[var(--color-text-primary)]`, inactive `text-[var(--color-text-tertiary)]`. **Neutral, never red** — several appear at once, so red here would break "keep red rare" even though red-on-active-toggle is otherwise sanctioned.
- **Form inputs:** `rounded-lg border border-[var(--color-border)] px-3 py-3 focus:border-[var(--color-border-focus)] focus:outline-none transition-colors`. Numeric inputs add `text-center text-xl font-tabular font-medium`.
- **Range slider (`RangeField`):** for a bounded setting that reads as a dial rather than a typed value — currently only the fueling carbs/hour target. Apply the `.range-input` class defined in `globals.css`; the track and thumb sit behind vendor pseudo-elements (`::-webkit-slider-runnable-track`, `::-moz-range-thumb`, …) that Tailwind utilities cannot reach, so this one control is styled there rather than inline. Track `0.25rem` in `--color-border`, thumb `1rem` in `--color-red-primary` (greying to `--color-text-tertiary` when disabled). Red is sanctioned here for the same reason as the primary toggle: it's a single instance, not a repeated one. Pair it with a `font-tabular` value readout beside the label and a plain-language hint below the track.
- **Gradient meter (`OpportunityMeter`):** for placing one already-displayed figure on a fixed scale and naming it — currently only the Impact breakdown's total. It is **not** a progress bar and has no second instance planned. Wrap it in the section's tile recipe (`rounded-xl border border-[var(--color-border)] bg-[var(--color-bg-elevated)] p-4`) so it reads as part of the panel it concludes rather than as a section of its own. Track `h-2 rounded-full` carrying the `.opportunity-track` class from `globals.css` (gradient geometry in CSS, every stop a token, following the `.hero-scrim` precedent) — never an inline gradient. **The bar spends the colour and nothing else does:** the verdict word and the marker both stay `--color-text-primary`. Tinting the word to match the marker's stop was the first draft and it reads as two instruments shouting the same thing, which is what "findable, not loud" rules out. The marker is a 2px tick ringed in the tile's own background so it stays visible over the deep-red end and the green end alike, in both themes; its `left` percentage is the only inline style and it is clamped a hair inside the ends so an extreme reading is still a tick on the bar and not a cut edge. Give the track `role="img"` and an `aria-label` that names the band and the figure in words: **a gradient is never the only carrier of a reading**, and a green-to-red ramp is the one thing dichromacy compresses hardest. **The gradient stops and the axis labels are both pinned to the band thresholds, and neither is evenly spaced.** The stops put orange on the challenging/moderate edge and lime on the moderate/favorable edge so the pixel under the marker changes family where the verdict word changes; the three labels are absolutely positioned over the MIDDLE of their own band rather than spread edge to edge. Evenly spaced stops and `justify-between` labels both shipped first and were wrong together: the word flipped to Favorable at 55 while the bar stayed amber until 86 and the centred "Moderate" label sat at 50, so on a cool day **82% of races rendered the word "Favorable" over a yellow pixel under the label "Moderate"**. Derive both from the thresholds, never hardcode them, and do not "tidy" the stops back to 20% steps. Label them in `font-tabular text-[10px] text-[var(--color-text-tertiary)]`, and do not reprint the number the row above already carries.
- **Data tables:** wrapper `overflow-x-auto rounded-2xl border border-[var(--color-border)]`; header row `bg-[var(--color-bg-elevated)]` with eyebrow-styled cells; body rows separated by `border-t border-[var(--color-border)]` (no zebra); numeric cells `font-tabular` right-aligned.
- **Stat blocks:** eyebrow label (column-header style) + value `text-2xl font-tabular font-medium text-[var(--color-text-primary)]`, arranged in a `grid grid-cols-3` row bounded by `border-t border-b`.
- **Modal (`PrintModal`):** the app's only centered overlay — a support/ad gate in front of `window.print()`. Backdrop `fixed inset-0 z-50 flex items-center justify-center bg-[var(--color-scrim)]/40 p-4 print:hidden` (the scrim is a token at 40%, not a new color). Panel `w-full max-w-md rounded-2xl border border-[var(--color-border)] bg-[var(--color-bg-surface)]` — **no shadow**, per "borders over shadows"; header and footer are separated by `border-b`/`border-t` rather than spacing alone. Exactly one red primary action (Print) in the footer; the ✕ is neutral `text-secondary`. Dismissal reuses `usePopover` from the caller (Escape, outside pointer-down), with focus moved to the primary action on open. Reserve this pattern for actions that genuinely warrant blocking the page — inline popovers (`DatePicker`, `TimePicker`) remain the default for in-form choices.
- **Dropdown (`<select>`):** `appearance-none` plus a `<SelectChevron />` inside a `relative` wrapper — never the platform arrow and never a filled `▾`/`▼` glyph, which inherits the font's shape and lands heavier than every other arrow in the app. The chevron is the same `1.75`-stroke inline SVG as the disclosure toggle, pointing down (`viewBox="0 0 20 20"`, path `M4.5 7.5 10 13l5.5-5.5`, `h-4 w-4`, `--color-text-secondary`); position it with a `right-*` class and leave right padding on the select wide enough to clear it. Used by `RaceYearPicker` and the calendar's `FilterSelect`.
- **Disclosure toggle:** a `<button>` styled as an eyebrow (`text-xs font-medium uppercase tracking-wider text-[var(--color-text-secondary)] hover:text-[var(--color-text-primary)]`) with `flex items-center gap-1.5`, prefixed by a chevron — never a `+`/`−` glyph. The chevron is a `1.75`-stroke inline SVG (`viewBox="0 0 20 20"`, path `M7.5 4.5 13 10l-5.5 5.5`, `h-3.5 w-3.5`), matching the stroke weight used in `DatePicker`'s calendar-nav arrows. It points right (`M7.5 4.5 13 10l-5.5 5.5` as drawn) when collapsed and rotates to point down via `rotate-90 transition-transform duration-150` when expanded (driven by `aria-expanded`). Avoid appending a numeric value summary to the collapsed label (e.g. no "(120 g/hr)"); a plain on/off state suffix like " (on)" is acceptable where the section has a binary enabled state. **Nothing currently implements this.** It was documented here as in use in `InputForm` for some time after the Weather & Wind and Fueling Strategy sections it named were flattened into plain labels, and the hill-segments section on `/results` was briefly a disclosure before being made permanent. If a section needs collapsing again, build the chevron from this spec rather than looking for a component; a spec with no implementation is honest, a spec that claims one is how this line went stale twice.

## Marketing bands (home page)

The home page is a stack of **full-bleed bands** below the hero, following the mcmillanrunning.com rhythm in structure only — none of its palette. Components live in `src/components/home/`.

- **Band:** `<section className="w-full">` edge to edge, with an inner `<div className="mx-auto max-w-7xl px-6 py-20">`. Adjacent bands are separated by `border-y border-[var(--color-border)]` and an alternating `bg-[var(--color-bg-elevated)]` fill — never a shadow or a gap alone. Prose-only bands (the closing CTA) narrow to `max-w-3xl` and `py-24`.
- **Feature row (`FeatureRow`):** `grid items-center gap-12 lg:grid-cols-2 lg:gap-16`, alternating sides via `lg:order-last` on the copy column. The media column carries `min-w-0` so a wide child (chart SVG, table wrapper) shrinks inside its grid track instead of forcing the page to scroll sideways.
- **Bullet mark:** a `1.75`-stroke inline check SVG (`viewBox="0 0 20 20"`, path `M4.5 10.5 8 14l7.5-8`, `h-4 w-4`) in `text-[var(--color-text-tertiary)]` — **neutral, never green**. Green stays reserved for a faster-than-goal delta; a decorative green tick here would break that the way a decorative red would break red.
- **Media is real product UI, never a screenshot.** `computePaceChart` is pure, so `src/components/home/demoResult.ts` builds a real `PacingResult` at module scope and the rows render the actual `ElevationChart`. The page below the hero is a server component, so this runs at build time. Marketing imagery therefore cannot drift out of date with the product, and there is no image weight. Do not import `SummaryHeader` for this — it carries the Stripe/analytics order flow.
- **`PaceBandPreview` is the one sanctioned facsimile.** `PaceBand` is `hidden print:block` with all geometry in the `@media print` block, so it renders as nothing on screen. The preview is a deliberately partial rem-scaled copy (same wordmark bars, columns, and droplet mark) — a teaser, not the band.
- **One red action per page.** The closing CTA's button is the home page's only red besides the hero's Calculate. Course cards and "How it works" links are neutral text/border treatments.

## Printed paceband (`PaceBand.tsx` + `@media print` in `globals.css`)

The only printed surface. Reference dimensions were taken by measuring
paceband.org's print PDF against ours (Aug 2026, both printed from Chrome on
US Letter) — theirs is the wrist-band size runners actually wear:

- **Strip width: 1.3in** (paceband.org measures ≈1.28in; our first pass at
  1.7in printed noticeably too wide to wrap a wrist band).
- **Row height ≈ 11.5pt, 7pt tabular type** — 43 km rows plus wordmark bars
  land at ≈7.4in tall, close to their ≈7.2in. Height only needs to be
  "roughly the same"; width is the constraint that matters for wearing it.
- Wordmark bars top and bottom print in `--color-text-primary` with
  `print-color-adjust: exact`; hairline row borders, no zebra (their
  navy/yellow banding is their brand, not ours).
- The gel cue is a **droplet** icon in `--color-red-primary` (mirrors
  paceband.org's droplet service icons), one per row that carries a
  `FuelingCue`; the column disappears entirely when fueling is off.
- All sizing lives in pt/in inside the `@media print` block so the printed
  scale is independent of screen rem.

## What NOT to do

- Do not introduce new colors. Red, white, black (plus grayscale neutrals), the reserved semantic green **in its two roles**, the closed six-stop course-profile ramp below, and the single blue of the precipitation glyph. Nothing else, and nothing new for a second scale.

- **Green has two roles, for the same reason red does, and they are not interchangeable.** `--color-green-primary` is a text and data-mark green: the faster-than-goal delta, the Downhill profile pill, a bar below the line. `--color-green-fill` is a quiet tint that sits *under* dark text, and it belongs to one thing: the calendar chip for a race whose day is inside the 5-day forecast horizon (ROADMAP #19). **Note the asymmetry with red:** `--color-red-fill` is a fill under *white* text and is identical in both themes; `--color-green-fill` is a tint under `--color-text-primary` and differs per theme, because a pale mint on a near-black page is a lamp and the annotation would outshine the content it annotates. Do not pair white text with the green fill, and do not reach for it as a generic "success" surface.

- **That marker shipped three times, and the two failures are the useful part.** The first cut was a 3px `--color-green-primary` left rule on the chip: faithful to "keep green rare", and **effectively invisible** — in a grid of pale chips a hairline reads as a rendering artefact rather than a signal, and a signal nobody sees is not restraint, it is a feature that did not ship. The correction overshot: a `#DCFCE7` fill at **84% HSL saturation**, outlined in `--color-green-primary`. On a page whose palette is red, white, black and grayscale, that was not an annotation but the loudest thing on the screen, and the near-black-green 1px outline made the chip read as **selected** rather than annotated, which is a claim about state the calendar does not make. The settled version tints only: `--color-green-fill` at 44% saturation, the same neutral `--color-border` every other chip carries, and `--color-text-primary` for the race name. **The general rule: on a near-monochrome page, the bar for a chromatic annotation is that it be findable, not that it be loud** — and both bounds are now enforced, since `globals.tokens.test.ts` asserts a ΔE floor against `--color-bg-elevated` so it cannot vanish and a saturation cap against `--color-green-primary` so it cannot creep back up.

- **The race name inside a marked chip stays `--color-text-primary`, and the chip's border stays neutral.** The name is the content and the colour is the annotation. Greening the text would read as a link state, and the chip is already a link; greening the border would read as selection. Only the legend swatch and the surface carry green.
- **Rain is blue, and that is the third and last exception.** `--color-blue-primary` colours the three falling strokes of the weather timeline's precipitation glyph, and nothing else on the site. The case it had to make, since the two above it took several attempts: rain is the only quantity here that readers arrive already holding a colour for. Every weather app they have opened draws falling water blue, so the colour is doing recognition work that no label placement can replace, and a monochrome version in a column headed "Rain chance" reads as a second cloud rather than as rain. Red and green could not be borrowed even if the palette allowed it, because both are *semantic* on this page (slower, faster, hotter, downhill) and rain has no opinion about pace.
  - **The cloud stays neutral; only the falling strokes are blue.** Colouring the whole glyph would make it a logo sitting in a table of grey marks. Colouring the part that is literally the rain keeps the annotation on the quantity.
  - **It is a mark, not an accent.** The percentage or the word beside it is what carries the claim (`rainText` branches on source, because the same stored number means three different things), so the glyph is decorative and `aria-hidden`. Do not reach for this token for text, a border, a fill, a link state or a second data series.
  - **Dark gets its own value** (`#79A8D8`), lighter and desaturated to 55% HSL against light's 70%, on exactly the rule the dark profile ramp follows: a fully saturated accent on a dark field vibrates. That puts it beside `--color-green-primary` (52%) and `--color-red-primary` (64%) rather than shouting past them. Light is 7.0:1 on white and 6.7:1 on `--color-bg-elevated`; dark is 7.5:1 on the page and 6.2:1 on the elevated surface, which is past AA even though the glyph is labelled in text and does not need to be.
  - **It was opened on an explicit call, not by drift.** The monochrome version shipped first and was the correct default; the reversal is recorded here so a future pass can see that "no blue" was considered and overridden for one glyph, rather than never having been the rule.

- **Course profile carries a six-stop color ramp — one color per profile. This reverses a rule that stood until 2026-09-08, and then a second one written the same day**, so both earlier arguments are recorded here rather than deleted.
  - **The original rule:** a flat/rolling/hilly/mountainous scale is the obvious place to reach for four new colors, so `DifficultyBadge` took red on the two hardest bands only and left the rest neutral, because making red common is the one thing this palette is built to prevent.
  - **The first reversal (three tiers):** the taxonomy changed, not the taste. The badge speaks findmymarathon.com's six labels (Very Flat / Mostly Flat / Rolling Hills / Downhill / Hilly / Very Hilly) so runners read the same vocabulary comparing races there and here, and that vocabulary arrives with a color convention they already associate with it. It was grouped into three tiers — green for the profiles that make a course faster, orange for the middle pair, red for the two that cost you time — to add as few colors as possible.
  - **Why three tiers failed, and this is the useful part:** grouping the six into pairs gave **Mostly Flat and Rolling Hills the same pill**, and those are the two biggest bands in the catalog — 118 and 120 of 326 courses. On 73% of races the color said nothing the label had not already said, while still spending a color. Worse, the pair it collapsed is exactly the boundary runners care about: "do I need hill legs for this?" A ramp whose most common two steps are identical is not a ramp; it is three colors pretending to be six.
  - **The ramp now, fastest to hardest:** Downhill `--color-green-primary`, Very Flat `--color-lime-primary`, Mostly Flat `--color-gold-primary`, Rolling Hills `--color-orange-primary`, Hilly `--color-red-primary`, Very Hilly `--color-red-deep`. **Four of the six already existed** — only lime and gold are new tokens, and the dark end reuses the button-hover red rather than inventing a maroon.
  - **It is a scale, not a set of accents.** Hue falls monotonically at every step (147° → 124° → 70° → 47° → 35° → 32° in CIELAB), and the two red stops, which are only 3° apart, separate on lightness instead (6.47:1 against 10.02:1 on white). Adjacent stops are ΔE00 ≥ 10.2 apart, so no two read as the same color at 12px.
  - **findmymarathon's hue relationships were adopted; their hexes were not.** Theirs are Downhill `#179617`, Very Flat `#3ea618`, Mostly Flat and Rolling Hills both `#ff7800`, Hilly and Very Hilly both `#a6183e` — four colors over six labels, so their site has the same collapse ours had, and three of the four fail WCAG AA as pill text (`#ff7800` is 2.65:1 on white, both greens under 4:1). Ours clear AA on white **and** on `--color-bg-elevated`, where the pill also appears in table rows: 5.02, 4.99, 4.92, 5.18, 6.47, 10.02 on white. Matching their vocabulary is the point; matching their contrast failures is not.
  - **Color is never the only signal.** Each stop pairs with its own icon and its own word, which matters because a green-to-red ramp is the one thing dichromacy compresses hardest — under simulated protanopia the six stops fall to ΔE00 2.7 at the closest pair. The label carries the meaning; the color speeds up recognition for those who can see it. Do not "fix" this by adding a seventh color or a fill — the redundancy is the fix.
  - **The ramp has a second set of six for dark mode**, because the light hexes fail against a dark page (`#7F1D1D` is nowhere near readable there): Downhill `#68CF9A`, Very Flat `#8FC954`, Mostly Flat `#D3AE69`, Rolling Hills `#DB9E76`, Hilly `#E08571`, Very Hilly `#E66B6D`. Two things changed from light: they are lighter, and they are **desaturated** (HSL 52-71% against the light ramp's 69-96%), because a fully saturated accent on a dark field vibrates. The scale still behaves: hue falls at every step (158° → 126° → 83° → 59° → 38° → 25°), lightness descends gently with it (L\* 76 → 60) so harder still reads as heavier, every stop clears 4.5:1 on all three dark surfaces, and Very Hilly stays the darker of the two reds. Same closed set, not a licence for a third.
  - **`src/app/globals.tokens.test.ts` enforces all of it, once per theme** — six tokens defined, all distinct, neighbours ≥ 15 apart in CIELAB, every stop ≥ 4.5:1 on the page, surface and elevated surface, hue monotone, and the dark ramp under a 75% saturation ceiling (the vivid off-the-shelf brights this theme shipped first all fail it). A future pass that swaps in findmymarathon's own hexes to "match their site exactly" fails there, which is the point.
  - **This ramp has exactly two consumers: the profile pill and the pace opportunity meter.** It was the profile pill's alone until 2026-09-22, and the amendment is narrow. `OpportunityMeter` renders the same six stops, reversed, as the gradient on a single horizontal bar. **That is coherence, not a second scale:** both say the same thing in the same direction, fast to slow, and the meter's stops carry the identical meaning the pill's do at the identical positions. Inventing a separate red-amber-green for the meter would have been the actual violation of "nothing new for a second scale" — it would have put two unrelated fast-to-slow ramps on one page and invited the reader to work out whether they agreed. Reusing it also costs nothing: no new tokens, and `globals.tokens.test.ts` already fences all six for ΔE, contrast, hue monotonicity and the dark saturation cap. **A third consumer still has to make its own case**, and anything that wants four colors for something that is *not* a fast-to-slow scale still gets the answer the original rule gave.
- **The Race splits chart uses red above the line and green below, and that is the reserved pair, not a new scale.** `RaceSplitsChart` draws one bar per split row: how many seconds that kilometre (or mile) costs against flat ground. Red for a bar that costs time and green for one that gives time back is the same "slower than target / faster than target" semantic `SummaryHeader` already paints on its weather delta, applied to terrain instead of weather, so no third colour and no tint by steepness. Do not reach for the `DifficultyBadge` ramp here: that ramp names a whole course's profile, and a per-kilometre bar is not a verdict on a course. The named climbs are marked with a neutral `--color-bg-elevated` band **outlined in `--color-border`** — the fill alone is one step off the page background and invisible on a white surface, which is the whole job the band has.
- **`RaceSplitsChart` puts its axis labels and its hover tooltip in HTML and stretches its plot; `ElevationChart` does neither, and both are right.** The elevation chart keeps its aspect ratio, so text inside its viewBox scales predictably. The cost chart has to be short and wide on a phone and taller on a desktop, and scaling a viewBox to do that either smears the bars or shrinks 10px axis text to an unreadable four. So its plot carries nothing but rectangles and horizontal rules (which survive `preserveAspectRatio="none"`) and every piece of type, the tooltip included, sits outside it in ordinary HTML. Its tooltip is a single pill styled after the elevation chart's (a bold value in the reserved red or green, then quieter context), placed in the half of the plot the hovered bar is not in so the tallest bar is never the one it covers, and it is `aria-hidden` rather than a live region because it would otherwise be re-announced on every pointer move. Any new chart of bars should follow this one; any new chart of a continuous line should follow the elevation chart.
- **The chart's axis is symmetric about zero and never narrower than ±10s.** A flat course's bars are two-second dust, and an axis fitted to them would draw Chicago as a mountain range. The floor is what makes "this course is flat" visible as evidence rather than asserted in a sentence.
- **The profile badge's second pill — net elevation change — is still always neutral grey.** A net drop makes a course faster, but that is a fact about the course, not a verdict on the runner, and a second colored pill competes with the profile pill for the eye. On a Downhill course it would also only restate what the label already says. (Until 2026-09-08 that pill showed total gain, and briefly turned green on big descents; both were dropped.)
- **A verdict on the RUNNER does not belong on the results page.** `BqBadge` rendered under the results header from 2026-09-04 until 2026-09-20, and it was removed because it was the one element there that had nothing to do with the chart below it: everything else on that page describes a race and a plan for running it, while "Misses Boston by 1:05:00" judges the person. It now lives only on `/boston-qualifier`, which is where someone goes having asked the question. Nothing about the feature changed — `src/lib/bq/` and the page are untouched.
- **`BqBadge`'s own colors need no argument, and it stays two pills.** `SummaryHeader`'s "vs goal" note already paints slower-than-target red and faster-than-target green, so those two reserved semantics carry over unchanged. The **net-downhill index pill stays neutral** — an index is a fact about the course, true whoever runs it, not a verdict on the runner, and coloring it would imply the race did something wrong. A single chip would have to pick one of the two independent facts and misrepresent the other.
- Do not use shadows beyond the system default.
- Do not use red for decoration (backgrounds, hover states on non-interactive elements, etc.).
- Do not introduce new font sizes outside the typography scale.
- Do not use Tailwind's `zinc-*`, `gray-*`, or named-color utilities directly. Always reference design tokens.
- Do not hardcode `bg-white`/`text-black` or add `dark:` variants. Colors live entirely in the token values in `globals.css`, in both themes; a component never branches on the theme.
